# Модель данных ЕДИНСТВО

Статус: логическая модель для проектирования; это не применённая схема базы данных.

## Сущности первого этапа
- **users** — внутренний ID, статус аккаунта, даты создания/обновления.
- **auth_identities** — идентификатор провайдера и подтверждённый контакт; секреты аутентификации не хранить в открытом виде.
- **profiles** — user_id, отображаемое имя, псевдоним, биография, аватар, настройки видимости.
- **friendships** — инициатор, получатель, статус, временные отметки; уникальность пары и допустимые переходы статуса.
- **posts** — автор, текст, видимость, статус модерации, временные отметки.
- **post_media** — ссылка на управляемый объект хранения, тип, размер, автор загрузки; не принимать произвольные внешние URL как доверенные медиа.
- **comments** — публикация, автор, текст, статус модерации, временные отметки.
- **reactions** — пользователь, объект, тип реакции; ограничение против нежелательных дубликатов.
- **blocks** — кто кого заблокировал; блокировка влияет на видимость и взаимодействия на сервере.
- **reports** — заявитель, тип и ID объекта, категория, состояние обработки, временные отметки.
- **moderation_actions** — модератор, действие, причина, целевой объект, время; доступ ограничен.
- **notifications** — получатель, тип события, безопасная ссылка на объект, состояние прочтения.
- **audit_events** — минимальный журнал чувствительных действий без паролей, токенов и лишнего содержимого.

## Общие правила
- Использовать внутренние стабильные идентификаторы, а не email или псевдоним как первичный ключ.
- Внешние ключи и ограничения целостности обязательны.
- Добавлять временные отметки и определённые правила удаления/архивирования.
- Для лент и списков предусмотреть индексы и пагинацию.
- Права на чтение/изменение проверять для каждой записи на сервере.
- Не смешивать dev/test и production-данные.
- Миграции хранить в Git и применять контролируемо.
- Удаление аккаунта и связанных данных должно соответствовать утверждённой политике хранения и юридическим требованиям.

## До реализации схемы нужно решить
1. Какая система аутентификации выбрана и какие способы подтверждения доступны без обязательных платных сервисов.
2. Где хранятся изображения и какие ограничения размера/типа действуют.
3. Каковы точные правила видимости профиля, публикаций и комментариев.
4. Как долго хранятся жалобы, журналы модерации и резервные копии.

Не считать эту спецификацию реальной базой данных или работающей функцией.
