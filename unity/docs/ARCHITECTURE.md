# Архитектура ЕДИНСТВО

Версия документа: 1.0  
Статус: целевая архитектура; реализация ещё не завершена.

## 1. Архитектурная цель
Создать отдельную социальную платформу с веб-интерфейсом, серверным API и единым источником данных. Не превращать презентационную HTML-страницу в монолит, где бизнес-правила, доступ к данным и интерфейс неразделимы.

## 2. Логические слои
1. **Presentation** — адаптивный веб-интерфейс, доступность, навигация и состояния загрузки/ошибок.
2. **Application** — пользовательские сценарии: регистрация, вход, профиль, публикация, лента, комментарии, реакции, связи и уведомления.
3. **Domain** — правила владения данными, приватности, видимости контента, блокировок, жалоб и модерации.
4. **API** — проверяемые контракты запросов/ответов, аутентификация, авторизация, валидация и ограничения частоты.
5. **Data** — реляционная модель, ограничения целостности, миграции и индексы.
6. **Operations** — CI, окружения, логи без секретов, резервные копии, мониторинг и восстановление.

Слои взаимодействуют через явные интерфейсы. UI не обращается к базе напрямую в обход правил доступа; клиент не считается доверенной стороной.

## 3. Целевая структура кода
До реализации backend согласовать стек и ограничения инфраструктуры. Целевая структура проекта:
```
unity/
  index.html                  # текущая презентационная страница
  README.md
  docs/
    ARCHITECTURE.md
    PRODUCT-CONSTITUTION.md
    ROADMAP.md
    DATA-MODEL.md
    SECURITY-PRIVACY.md
    API-CONTRACTS.md
    QUALITY-RELEASE.md
  app/                        # будущий веб-клиент
  server/                     # будущая серверная логика/API
  database/
    migrations/               # версионируемые изменения схемы
    seeds/                    # только синтетические dev-данные
  tests/
    unit/
    integration/
    e2e/
  scripts/
  .github/workflows/          # CI для проекта, если workflow согласован
```
Это целевая схема, а не утверждение, что все каталоги и функции уже существуют. Не добавлять пустые каталоги только ради вида; создавать их вместе с первым проверяемым кодом.

## 4. Окружения и выпуск
- **Development** — локальная разработка и синтетические данные.
- **Preview/Staging** — проверка интеграции до production; тестовые данные и отдельные ключи.
- **Production** — только проверенный код и реальные данные.
- Секреты хранятся в настройках окружения/секрет-хранилище, не в Git.
- Миграции версионируются. Изменения схемы должны иметь безопасный порядок применения и план восстановления.
- Для каждого выпуска фиксируются commit, результат CI, проверка URL и способ отката.

Если отдельное staging-окружение требует платного ресурса, оно не создаётся без согласования; до этого используются локальные проверки и изолированное preview-окружение, если оно доступно.

## 5. Доменные модули MVP
- Identity & Access — регистрация, вход, сессии, восстановление доступа.
- Profiles — публичные поля, настройки видимости и управление аккаунтом.
- Social Graph — запросы в друзья, принятие/отклонение, блокировки.
- Content — публикации, редактирование, удаление и вложения.
- Feed — видимые пользователю публикации с пагинацией.
- Interactions — комментарии и реакции.
- Trust & Safety — жалобы, модерация, ограничения и аудит действий модераторов.
- Notifications — уведомления о событиях с настройками пользователя.

Модули используют единые идентификаторы пользователей и общие правила доступа. Не дублировать одну и ту же бизнес-логику в разных модулях.

## 6. Принципы API
- Версионируемые, документированные контракты.
- Проверка входных данных на сервере.
- Авторизация каждой операции на основе пользователя и ресурса.
- Пагинация списков, ограничение размеров тела запроса и вложений.
- Единый формат ошибок без утечки внутренних подробностей.
- Идемпотентность там, где повторный запрос может создать дубликат.
- Лимиты запросов и защита от злоупотреблений.
- Клиентские проверки удобны для пользователя, но не заменяют серверную валидацию.

## 7. Архитектурные запреты
- Никаких секретов в клиентском коде или репозитории.
- Никаких прямых ссылок на production-данные из тестов.
- Никаких обещаний полной безопасности без тестирования.
- Никакого подключения новой платной инфраструктуры без согласования.
- Никакого изменения MMW-COMPANY production в рамках разработки ЕДИНСТВО.
