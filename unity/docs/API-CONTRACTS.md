# API и интеграционные правила ЕДИНСТВО

Статус: проект контракта; endpoints ещё не реализованы.

## Общие правила
- Все ошибки имеют предсказуемую структуру: `code`, безопасное `message`, необязательный `requestId`.
- Не возвращать stack trace, SQL, секреты, токены или внутреннюю конфигурацию.
- Входные данные валидируются на сервере.
- Списки имеют ограниченную пагинацию и стабильную сортировку.
- Все защищённые маршруты проверяют сессию и права доступа.
- Запросы, способные создавать дубликаты при повторе, проектируются идемпотентно.
- Контракт API документируется и проверяется автоматическими тестами.

## Целевые группы маршрутов
- `GET /health` — состояние доступности без раскрытия внутренней конфигурации.
- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `POST /auth/recovery` — только после выбора и безопасной настройки auth-механизма.
- `GET /me`, `PATCH /me/profile`, `PATCH /me/privacy` — собственный профиль и настройки.
- `GET /feed` — лента только из доступных текущему пользователю публикаций.
- `POST /posts`, `GET /posts/{id}`, `PATCH /posts/{id}`, `DELETE /posts/{id}` — публикации с проверкой владельца и видимости.
- `GET /posts/{id}/comments`, `POST /posts/{id}/comments` — комментарии с проверкой доступа и модерации.
- `PUT /posts/{id}/reactions/{type}`, `DELETE /posts/{id}/reactions/{type}` — реакции.
- `POST /friend-requests`, `PATCH /friend-requests/{id}`, `POST /blocks`, `DELETE /blocks/{id}` — связи и блокировки.
- `POST /reports`, защищённые маршруты модерации — только для авторизованных ролей.

Эти маршруты иллюстрируют будущий контракт. Их наличие в документе не означает, что API уже существует.

## Проверки API
Для каждого маршрута описать: входные поля, ответ, ошибки, требования к авторизации, лимиты, приватность и тесты на доступ к чужим данным.
