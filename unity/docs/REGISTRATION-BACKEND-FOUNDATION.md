# ЕДИНСТВО — регистрация и запуск backend

Статус: foundation на отдельной рабочей ветке; пока не подключено к production и не применено к базе данных.

## Регистрация и одобрение
1. Пользователь вводит email, пароль, отображаемое имя и уникальный никнейм (3–24 символа: латиница, цифры, подчёркивание).
2. Supabase Auth создаёт identity; триггер создаёт профиль со статусом `pending`.
3. До одобрения пользователь видит только состояние заявки и не может создавать контент или сообщения.
4. Администратор с серверно установленным `app_metadata.unity_role=admin` проверяет заявку и принимает решение через защищённую серверную операцию.
5. При одобрении профиль становится `active`; при отказе — `rejected`. Админ не видит и не восстанавливает пароль пользователя.
6. Восстановление пароля — через Supabase Auth; ограничить частоту и не раскрывать, существует ли email.
7. Удаление аккаунта должно выполняться отдельным подтверждённым серверным сценарием после утверждения политики хранения.

## Доступы и безопасность
- Не использовать user_metadata для ролей или решений авторизации.
- Не помещать service_role/secret key в браузер, репозиторий, URL или логи.
- Перед созданием первого администратора определить подтверждённый аккаунт и выставить app_metadata через доверенный административный путь. Не реализовывать self-promotion из клиента.
- RLS включён на всех таблицах этой миграции; все права требуют проверки реальными интеграционными тестами.
- Контент при создании имеет статус `pending_review`; публикация требует модерационного действия.
- Не подключать эту схему к базам MMW-COMPANY или MMW-ORDER.

## Важные ограничения текущей миграции
- Это начальная схема, а не готовый публичный запуск.
- Админский API для approve/reject, безопасные уведомления, email templates, media storage policies, rate limits, CAPTCHA/abuse prevention, удаление аккаунта и e2e tests ещё требуют реализации.
- Политики видимости и связей требуют проверки на крайних случаях до подключения UI.
- Не применять к production без отдельной базы UNITY, тестового применения и проверки Supabase Security Advisors.

## Приёмочные сценарии
1. Повторный handle отклоняется ограничением уникальности.
2. Некорректный handle или пустое отображаемое имя не проходят валидацию.
3. Новый аккаунт получает `pending`; публикации и сообщения запрещены до одобрения.
4. Пользователь не может изменить `account_status`, `id` или `handle` через клиентский Data API.
5. Чужие приватные профили и черновики недоступны.
6. Блокировка исключает отправку сообщений и запросов связи в обе стороны.
7. Пользователь не может читать чужие личные сообщения, уведомления или жалобы.
8. Только серверно назначенный admin может видеть/изменять очередь модерации.
9. Удалённый Auth user удаляет профиль и зависимые пользовательские данные согласно FK-политике.
10. Выполнить advisors и negative tests на всех RLS-политиках до запуска.
