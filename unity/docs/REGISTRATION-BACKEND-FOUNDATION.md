# ЕДИНСТВО — регистрация, восстановление доступа и административный API

Статус: backend foundation плюс первая Edge Function; публичный сайт пока не подключён.

## Регистрация и вход

Регистрация выполняется через Supabase Auth API (`signUp`) с email, паролем и метаданными профиля `handle` и `display_name`. Триггер БД создаёт профиль со статусом `pending`; ограничения уникальности и формата применяются в БД. Пароль не хранится в `public.profiles`.

Перед подключением UI обязательно проверить в Supabase Dashboard, что подтверждение email включено, а redirect URLs ограничены адресами ЕДИНСТВА и локальной разработки. Не считать регистрацию готовой, пока не выполнен реальный тест подтверждения почты.

Вход — email + пароль. Подтверждение email и одобрение администратора — разные условия: подтверждённый пользователь остаётся `pending`, пока администратор не примет решение. RLS должна запрещать ему действия социальной сети.

## Восстановление пароля

Использовать Supabase Auth `resetPasswordForEmail` и штатный поток смены пароля. Интерфейс всегда показывает одинаковый ответ: «Если адрес зарегистрирован, инструкции будут отправлены», чтобы не раскрывать наличие аккаунта. Supabase Auth применяет лимиты на запросы регистрации/восстановления; до публичного запуска настроить CAPTCHA и проверить лимиты и SMTP. Не реализовывать собственные коды сброса пароля и не писать токены в логи.

## Административная Edge Function

Путь: `supabase/functions/unity-admin/index.ts`. Endpoint: `https://rgmdylzevxadiotmoglz.supabase.co/functions/v1/unity-admin`

Для каждого вызова требуется пользовательский Bearer JWT. Функция повторно проверяет пользователя через Auth API и проверяет серверно управляемое `app_metadata.unity_role === "admin"`; `user_metadata` не используется для полномочий. Только после этого выполняется операция с серверным secret key, который доступен только в runtime Supabase и не передаётся браузеру.

Поддерживаемые действия:
- `list_pending` — очередь заявок.
- `approve_account`, `reject_account`, `suspend_account`, `restore_account` — изменение статуса с обязательной причиной и записью действия модератора.
- `list_reports`, `resolve_report` — очередь и закрытие жалоб.
- `moderate_content` — скрытие, удаление или публикация материала, который ожидает проверки.

Все действия требуют администратора. CORS разрешает только origin сайта ЕДИНСТВА и локальные адреса разработки. При ошибках функция не возвращает содержимое секретов или внутренние сообщения БД.

## Назначение первого администратора

Не существует публичного кода, который выдаёт права. Сначала создайте отдельную учётную запись ЕДИНСТВА, подтвердите email, затем назначьте ей `app_metadata.unity_role=admin` через доверенный административный путь Supabase Dashboard/Management API. Не задавайте роль из клиентской формы и не используйте `user_metadata`. После назначения перелогиньтесь/обновите сессию, чтобы получить актуальные claims. Адрес администратора пока не зафиксирован, поэтому назначение не выполнено.

## Проверки и ограничения

Проверено ранее: 13 таблиц, RLS включён на всех 13, 36 политик, Security Advisor без findings на момент предыдущей проверки. Performance Advisor ранее показывал рекомендации по индексам и RLS initplan; это не блокирует разработку, но требует отдельной оптимизации.

Перед подключением сайта проверить:
1. Неверный/отсутствующий токен → 401.
2. Обычный пользователь → 403.
3. Администратор получает только очередь заявок/жалоб.
4. Повторный handle отклоняется.
5. Неподтверждённая почта не допускается к полноценному входу согласно настройке Auth.
6. Pending-пользователь не может создавать сообщения, связи или опубликованный контент.
7. Восстановление доступа не раскрывает существование email.
8. Все действия модерации создают audit trail; проверить ошибки записи журналов.
9. Проверить RLS негативными интеграционными тестами.

Функция не подключает и не изменяет сайт автоматически. До завершения тестов не считать весь пользовательский путь production-ready.
