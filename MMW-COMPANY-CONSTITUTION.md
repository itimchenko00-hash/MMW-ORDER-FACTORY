# MMW-COMPANY — рабочий стандарт проекта

## 1. Коммерческая чистота
Публичные страницы не показывают внутренние технические термины, служебные названия, отладочный код, внутренние идентификаторы или техническую документацию.

## 2. Замена, а не наслоение
При изменении блока старый слой заменяется. Нельзя оставлять предыдущую фотографию, текст, компонент или обработчик поверх нового.

## 3. Медиа
Каждый смысловой блок получает тематическое медиа или уместную инфографику. Одна и та же фотография не повторяется внутри одного проекта без обоснованной продуктовой причины. Финальные изображения хранятся локально в папке соответствующего проекта.

## 4. Семантическое соответствие
Изображение выбирается по смыслу конкретного текста, а не как декоративная случайная иллюстрация.

## 5. Интерактивность
Интерактивная карточка должна открывать именно тот текст, медиа и действие, которые относятся к выбранной карточке. Не допускаются дубли автоматически открытого и выбранного состояния.

## 6. Честность проекта
Концептуальные проекты обозначаются как концепции. Непроверенные показатели, площадки, доходность, сроки и результаты не выдаются за факты.

## 7. Экономика
Экономические модели работают только с введёнными пользователем данными и не подменяют финансовую проверку. Публичные обозначения должны быть понятны клиенту и инвестору.

## 8. Разделение проектов
Медиа, тексты и логика одного проекта не смешиваются с другим. Изменения CARPATHIA не должны повреждать ALADIN или завершённые проекты.

## 9. Проверка перед публикацией
Перед запуском проверяются синтаксис, локальные пути, уникальность медиа, интерактивность, адаптивность, отсутствие дубликатов и отсутствие технического текста в публичном интерфейсе.

## 10. Сохранение состояния
Перед существенной переработкой создаётся точка восстановления. Текущий CARPATHIA аудит защищён веткой `CARPATHIA-AUDIT-SNAPSHOT-2026-10-04`.

## 11. Метод безопасного подбора и импорта медиа
Если для проекта отсутствует подходящее локальное медиа, применяется отдельный двухэтапный метод, отработанный на CARPATHIA ECO LODGE:

1. Сначала полностью очищается старый медиаслой конкретного проекта, включая дублирующиеся изображения и старые привязки. Контентные блоки при этом сохраняются.
2. Для каждого смыслового блока составляется точная семантическая задача изображения.
3. Проводится внешний поиск конкретных фотографий по смыслу текста, а не по общему названию проекта.
4. Для каждого выбранного изображения фиксируются источник, автор и условия использования.
5. До завершения импорта внешние URL не используются в публичном runtime проекта.
6. Выбранные изображения импортируются в локальную папку соответствующего проекта и получают однозначные имена по смыслу блока.
7. После локального импорта изображения подключаются только локальными путями проекта.
8. Перед публикацией проверяются наличие каждого файла, отсутствие повторов, соответствие изображения тексту, отсутствие внешних image URL и отсутствие старых медиапривязок.
9. Если автоматический импорт через инфраструктуру проекта не выполняется, внешний URL не оставляется как обходной путь: проект сохраняется в чистом медиабезопасном состоянии до успешного локального импорта.
10. Этот метод является стандартным инструментом для последующих случаев замены, восстановления или первичного наполнения проектного медиаслоя.

## 12. Безопасный импорт локального медиа через временный branch-scoped workflow
Если стандартный импорт изображений через доступные инструменты проекта не позволяет безопасно получить бинарные файлы в репозиторий, применяется проверенный резервный способ:

1. Создаётся отдельная временная ветка только для импорта конкретного проекта.
2. В эту ветку добавляется временный GitHub Actions workflow с минимальным разрешением `contents: write`.
3. Workflow скачивает только заранее утверждённые изображения по конкретным прямым URL источников, без изменения публичного runtime.
4. До коммита workflow проверяет тип файла, допустимый формат, наличие файла, ненулевой размер и ожидаемое количество файлов.
5. Для каждого импортированного файла рассчитывается SHA-256; дубликаты по содержимому не допускаются.
6. Загруженные изображения сохраняются только в локальной папке соответствующего проекта с однозначными семантическими именами.
7. После успешного импорта workflow удаляет сам себя из ветки, чтобы временная инфраструктура не оставалась частью проекта.
8. После этого локальные файлы подключаются в runtime только абсолютными локальными путями проекта.
9. Источник, автор и условия использования каждого изображения фиксируются в отдельном реестре медиа.
10. Перед слиянием в рабочую ветку проверяются бинарные файлы, уникальность SHA-256, отсутствие внешних image URL, отсутствие старых привязок и соответствие каждого файла назначенному смысловому блоку.
11. Временная импортная ветка и workflow не считаются частью постоянной архитектуры проекта; постоянным результатом является только проверенный локальный медиаслой и его реестр.
12. Этот способ применяется только как контролируемый fallback при проблеме импорта и не отменяет остальные требования разделов 3, 4, 8 и 9 настоящей Конституции.
