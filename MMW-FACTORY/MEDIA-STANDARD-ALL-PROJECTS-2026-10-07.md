# MMW FACTORY — ЕДИНЫЙ СТАНДАРТ МЕДИАСЛОЯ ВСЕХ ПРОЕКТОВ

Дата фиксации: 2026-10-07
Статус: ОБЯЗАТЕЛЬНЫЙ СТАНДАРТ

## 1. Цель

Все продуктовые страницы MMW-COMPANY используют один и тот же медиаслой по архитектурному принципу, который доказал работоспособность на MMW-COMPANY:

WEB SOURCE → CONTROLLED IMPORT → LOCAL FACTORY ASSET → PROJECT MEDIA MAP → CANONICAL RENDERER → SEMANTIC PLACEMENT → ROUTE → SERVER ASSET DELIVERY → QA → LIVE.

Разница между проектами допускается только в содержании, визуальном характере и семантике изображений. Технический контракт медиаслоя не меняется от проекта к проекту.

## 2. Обязательные правила

1. Изображение сначала выбирается по смыслу конкретного блока, затем импортируется.
2. В runtime запрещены внешние image URL.
3. Рабочий сайт использует физически локальные assets из репозитория.
4. Для каждого проекта существует единый media map, являющийся единственным источником привязки изображений к проекту.
5. Renderer получает изображения только через канонический медиаконтракт.
6. Один проект = один канонический SPA route: #/project/<project-id>.
7. Legacy HTML route не имеет отдельной копии страницы; он только перенаправляет на канонический route.
8. Импорт считается завершённым только после проверки: файл существует → путь корректен → renderer использует файл → server отдаёт файл → live-страница показывает файл.
9. Каждая импортированная фотография имеет provenance в SOURCES.md: имя файла, исходный URL, автор/источник при наличии, назначение, дата импорта, основание использования/лицензия.
10. Повторное использование одной и той же фотографии в разных смысловых ролях запрещено без обоснованного исключения.
11. Пустой media map допустим только для проекта, который сознательно находится до этапа медиаподбора. Пустой map не считается ошибкой архитектуры; это состояние «media pending».
12. Нельзя создавать проект-специфический обход канонического renderer только ради фотографий.

## 3. Структура assets

Рекомендуемый путь:

public/ASSETS/<PROJECT>/photos/web-selected/

При необходимости допускаются отдельные подкаталоги для сезонных, hero- или иных специальных наборов, но они также должны быть локальными и отражены в provenance.

## 4. Семантическая модель

Каждое изображение получает одну роль, например:

- hero — главное визуальное представление проекта;
- product — продукт/объект;
- context — место и окружение;
- process — процесс реализации;
- audience — пользователь/клиент;
- economics — экономический контур;
- operations — эксплуатация/сервис;
- team — команда/взаимодействие;
- risk — риск/контроль;
- next — следующий шаг.

Название файла и media map должны позволять понять его назначение без открытия сайта.

## 5. Что запрещено

- hotlinking внешних фотографий;
- runtime-загрузка с Pexels/Unsplash/других сайтов;
- смешивание нескольких независимых media maps для одного проекта;
- скрытые fallback-изображения, которые подменяют отсутствующий asset и создают ложное ощущение корректности;
- копирование одного файла под разные имена без изменения визуального содержания;
- дублирование одинаковой фотографии в нескольких карточках без необходимости;
- отдельная legacy-страница с собственным renderer;
- принятие media import только по факту наличия файла в GitHub.

## 6. Обязательный QA

Перед LIVE проверяются:

### A. Asset
- файл существует;
- MIME/расширение корректны;
- файл читается;
- путь локальный.

### B. Provenance
- SOURCES.md существует для web-selected набора;
- source URL и назначение зафиксированы.

### C. Renderer
- проект использует канонический renderer;
- media map подключён;
- отсутствуют runtime external image URLs.

### D. Route
- canonical SPA route работает;
- legacy route не создаёт отдельную страницу.

### E. Delivery
- сервер реально отдаёт каждый локальный asset;
- нет ошибки 404/500 на asset path.

### F. UX
- изображение соответствует смыслу блока;
- карточка/секция не ломается без изображения;
- mobile layout не ломается;
- интерактивность не зависит от внешнего источника.

### G. Commercial cleanliness
- нет повторяющихся фото без причины;
- нет визуального мусора;
- нет технического текста в пользовательском интерфейсе;
- изображения не противоречат статусу «концепт».

## 7. Проектный lifecycle

Статусы медиаслоя:

MEDIA-PENDING → MEDIA-IMPORTED → MEDIA-MAPPED → MEDIA-RENDERED → MEDIA-QA-PASS → LIVE.

Нельзя объявлять проект MEDIA-QA-PASS только по успешному импорту.

## 8. Единый принцип для всех текущих проектов

Применяется одинаковый контракт к:

- ALADIN RESIDENCE
- NEXUS WORK
- NEXUS LOGISTICS
- CARPATHIA ECO LODGE
- AGROHUB
- ENERGY PARK

MMW-COMPANY остаётся эталоном рабочей реализации медиапротокола, но не отдельным техническим исключением.

## 9. Контрольная формула

Правильное состояние:

локальный файл
+ provenance
+ media map
+ canonical renderer
+ canonical route
+ server delivery
+ semantic placement
+ QA
= готовый медиаслой проекта.

Наличие только фотографии в репозитории не означает готовность.
